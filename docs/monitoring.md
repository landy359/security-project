# MemWatch v2 · 실행 중 프로세스의 메모리 이상 및 코드 변조 탐지

MemWatch는 Linux에서 선택한 프로그램을 실행하고, 영역별 실제 상주 메모리(RSS)와 네이티브 실행 코드의 변경을 감시한다. 웹에서 프로그램을 선택하면 해당 프로그램의 기준값, 경고, 이벤트와 리포트를 확인할 수 있다. 기본 대상은 이미지 뷰어와 지뢰찾기다.

## 기존 Docker 데스크톱에서 실행

압축을 풀어 `MemWatch-v2` 폴더를 컨테이너에 연결된 `Codes` 안에 둔다. 기존 v1 폴더와 나란히 둘 수 있다. `security-desktop` 컨테이너를 시작한 뒤 [Ubuntu 데스크톱](https://127.0.0.1:3001)의 XFCE 터미널에서 실행한다.

```bash
cd /workspace/MemWatch-v2
python3 -m venv --system-site-packages /config/memwatch-venv
/config/memwatch-venv/bin/python -m pip install -r requirements.txt
/config/memwatch-venv/bin/python app.py --data /config/memwatch-data-v2
```

Python 3.10 이상, Flask 3.1, Tk가 필요하다. Ubuntu에서 시스템 Python에 해당하는 패키지는 `python3-venv`, `python3-tk`다. 같은 컨테이너 사용자에게 실행·읽기 권한이 있어야 한다. 브라우저는 [감시 대시보드](http://127.0.0.1:5000)를 연다. 기존 수업 환경처럼 웹 포트를 호스트 루프백(`127.0.0.1:5000:5000`)에 게시하는 단일 사용자 구성이다.

## 첫 감시와 정상 작업 측정

1. **감시 대상**에서 앱을 선택하고 **작업을 마칠 때까지 측정**을 누른다. 새 프로세스가 열린다. 이미지 뷰어에서는 예제와 평소 크기의 파일을 열고 확대·축소·닫기를 반복한다. 지뢰찾기에서는 여러 판을 진행하면서 칸 열기, 깃발, 새 게임을 섞는다. 실제 감시에서 자주 겪는 가장 큰 정상 작업도 포함한다.
2. 기본 최소 12개 표본을 채우면 **이번 실행 측정 완료**가 나타난다. 계속 작업하는 동안 표본을 수집하므로 충분히 사용한 뒤 누른다. 같은 방식으로 기본 3번의 독립 실행을 마친다. 시간 고정 측정은 **정상 실행 반복 측정**을 사용한다.
3. 영역별 최소·최대·Limit·위험 경계와 작업 중 추가로 로드된 실행 매핑을 검토하고 **측정값 저장**을 누른다. 측정을 취소하거나 실패하면 이전에 저장한 기준을 사용한다. **감시 시작**으로 현재 프로세스를 감시한다.
4. 별도 실행을 검증하려면 **대상 종료 → 대상 실행 → 감시 시작**을 선택해 새 PID에서 정상 작업을 반복한다. 감시 중 RSS가 커졌다는 이유로 정상 기준을 자동 확장하지 않는다. 정상 작업에서 경고가 반복되면 해당 작업을 포함해 다시 측정한 뒤 검토·저장한다.
5. **대상 종료** 후 다른 앱을 선택한다. 대상 전환 시 최근 그래프와 임시 허용 상태가 초기화되고 선택한 앱의 저장된 기준과 이벤트를 불러온다. **현재 매핑 주소와 권한 보기**는 조회 시점의 실제 가상 주소 범위·권한·RSS를 표시한다.

측정/종료 시 대상 프로세스가 닫히므로 등록한 앱의 편집 내용은 먼저 저장한다. 여러 번 실행해도 짧거나 편중된 정상 표본만 수집하면 이후 정상 작업에서 경고가 발생할 수 있다. 동일한 형태의 정상 작업도 앱 버전, 입력 크기와 실행 환경에 따라 RSS가 달라질 수 있다.

## 다른 프로그램 등록

서버 실행자가 JSON 파일을 만든다. 각 항목에는 고유 ID, 화면 이름, 실행 인수 배열이 필요하다. 아래 예제는 Ubuntu의 일반 프로세스로 실행 경로를 확인하는 용도다.

```json
[
  {
    "id": "idle-worker",
    "label": "대기 프로세스",
    "argv": ["/bin/sleep", "600"],
    "startup_seconds": 1,
    "exercise": "대기 상태의 메모리와 코드 매핑을 관찰하세요."
  }
]
```

`python app.py --targets targets.json --target idle-worker`로 시작하면 등록한 프로그램이 선택 목록에 추가된다. `argv[0]`에는 컨테이너 안의 절대 실행 경로를 쓴다. `cwd`는 설정 파일 기준 작업 폴더이며 기본값은 해당 파일의 폴더다. 등록 앱은 초기화 대기 시간(기본 2초) 후 측정한다. 내장 앱은 창 준비 신호를 사용한다. 웹에서는 등록된 ID만 선택한다. 대상은 직접 실행한 단일 자식 PID이므로 스스로 백그라운드로 분기하거나 기존 앱에 요청만 전달하고 종료하는 런처는 실제 작업 프로세스를 관찰할 수 없다.

## 탐지 결과와 대응

| 관측 | 대시보드와 엔진의 동작 |
|---|---|
| RSS가 주의 경계 초과 | 영역별 초과량을 표시한다. **이번 경고 허용**은 RSS를 다시 읽고 코드 해시 일치를 확인한 뒤 해당 경고만 임시 허용한다. |
| RSS가 위험 단계에 진입 | 즉시 해시를 검사하고 위험 상태를 유지한다. 위험에는 임시 허용을 적용할 수 없다. |
| 파일 기반 실행 매핑의 해시 불일치 | RSS가 정상이어도 자식에 SIGSTOP을 보내고 커널 정지 상태를 확인한 뒤 동결을 표시한다. |
| 코드 검사 미확인 | 원인을 기록하고 임시 허용을 해제한다. 같은 검사에서 확인된 내용 불일치가 있으면 동결한다. |
| 사용자 재개 | SIGCONT 결과를 확인한다. 변경이 남아 있으면 다음 검사에서 다시 동결된다. |

## 측정·판정 기준

- RSS는 `/proc/PID/smaps`의 각 매핑에 있는 `Rss:` 값을 KiB 단위로 합산한다. 표와 그래프에는 MiB로 환산한다.
- **코드**는 실행 권한이 있는 매핑 전체, **힙**은 `[heap]`, **스택**은 커널이 스택으로 표시한 매핑, **익명**은 이름 없는 매핑과 이름 붙은 익명 매핑, **기타**는 남은 매핑이다. 각 매핑은 한 번만 합산한다. Python 객체와 이름 없는 스레드 스택 등 용도를 단정할 수 없는 메모리는 익명 항목에 포함될 수 있다.
- 정상 Limit은 정상 관측 최댓값에 **최댓값의 10%, 관측 범위(최대−최소), 영역별 최소 여유** 중 가장 큰 값을 더한다. 위험 경계는 Limit에 **Limit의 20%, 영역별 최소 여유** 중 큰 값을 더한다. 경계와 같으면 낮은 단계로 처리한다. 최소 여유는 스택 128 KiB, 코드·힙·기타 512 KiB, 익명 1 MiB, 전체 1.5 MiB다.
- 기본 주기는 RSS 1초, 해시 10초다. 기준 측정은 매 실행 준비 후 2초 안정화, 12개 표본, 총 3회다. 아래와 같이 수업 환경에 맞춰 조정할 수 있다. `--margin`과 `--danger`는 새로 측정하고 저장할 기준에 적용된다.

```bash
python app.py --demo --rss-seconds 1 --hash-seconds 5 --samples 15 --runs 3 --margin 0.10 --danger 0.20
```

- 해시는 `/proc/PID/maps`에서 읽을 수 있고 쓰기 권한이 없는 파일 기반 실행 매핑을 식별한 뒤 `/proc/PID/mem`을 읽기 전용으로 열어 각 매핑 전체에 SHA-256을 계산한다. 경로·파일 오프셋·길이·권한 조합으로 같은 매핑을 대응시켜 실행마다 달라지는 시작 주소에 의존하지 않는다.
- 확인된 내용 불일치는 RSS와 독립적으로 동결한다. 경미한 RSS 초과는 승인 때 검사하고, 위험 단계에 새로 진입하면 즉시 검사한다. 임시 허용은 현재 경고 영역과 단계 조합에만 적용되며 정상 복귀·단계 변경·대상 교체 시 만료된다.
- 권한 오류, 짧은 읽기, 처음 보는 실행 매핑의 추가·필수 매핑 누락, 동일 키 중복, 검사 도중 매핑 변화는 미확인으로 기록한다. 읽기 가능한 동일 매핑에서 별도로 확인한 해시 차이는 기록하고 대응한다. vDSO, 익명 실행/JIT 영역 등 비교에서 제외한 매핑 이름은 검사 상세에 표시한다. Python 소스·바이트코드·일반 데이터의 내용은 네이티브 코드 해시의 보장 범위 밖이다.
- 정상 기준은 신뢰하는 실행에서 만들어야 한다. 정상 업데이트나 라이브러리 변경도 차이를 만들 수 있다. 해시 읽기는 코드 페이지를 메모리에 올릴 수 있으므로 기준 수집 때도 해시 검사를 수행한다.

정상 측정 시작 시의 파일 기반 실행 매핑은 필수다. 신뢰하는 정상 작업 중에 추가로 관찰한 매핑은 별도로 저장한다. 이 매핑은 다시 로드될 때마다 같은 해시를 요구한다. 필수 매핑이 사라지거나 등록되지 않은 매핑이 생기면 미확인으로 기록한다. 샘플링 간격보다 짧은 변화나 실행 코드 밖의 데이터 값 변경은 이 방식에서 놓칠 수 있다.

## 기록과 검증

SQLite에는 대상별 기준과 이벤트를 저장한다. 외부 대상은 등록 ID, 실행 인수, 작업 폴더와 준비 대기 설정을 기준으로 프로필을 구분한다. 아키텍처와 감시기 Python 런타임 태그도 반영한다. 재시작 후에도 같은 데이터 폴더를 지정하면 이전 기준을 사용한다. 경고·승인·검사·시그널 이력은 대상별로 조회하고 CSV로 내보낼 수 있다. 그래프는 현재 감시의 최근 240개 RSS 표본을 표시한다.

```bash
cd /workspace/MemWatch-v2
/config/memwatch-venv/bin/python -m unittest discover -v
```

Linux 통합 테스트에는 C 컴파일러(`cc`)가 필요하며 두 GUI 검사는 XFCE 또는 Xvfb의 `DISPLAY`를 사용한다. 뷰어 검사는 별도 PID에서 이미지 열기·확대·축소·닫기 64회 동안의 경고 횟수와 최종 해시를 출력한다. 등록한 `/bin/sleep`도 같은 엔진으로 감시하고 실제 동결·재개를 확인한다. 제어된 검증용 자식은 자기 메모리에 부하를 주거나 자체 라이브러리 버전을 바꾸며 실제 RSS 변화와 해시 불일치 대응을 검사한다.

수업에서 이 과정을 직접 시연할 때는 같은 디렉터리에서 아래 명령으로 별도 시연 대상을 활성화한다. 시연 기준을 측정·저장한 뒤 감시를 시작하고 대상 창의 **+1 MiB**, **메모리 해제**, **v2로 교체**, **v1 복원**을 사용한다. 시연 전용 프로필과 매핑 별칭은 일반 대상과 분리한다.

```bash
/config/memwatch-venv/bin/python -m tests.build_demo
/config/memwatch-venv/bin/python app.py --demo --data /config/memwatch-data-v2
```
